# Sid Agarwal

A personal site for projects, writing, background, and reading, with a browser-based desktop and alternate portfolio views.

Public site: https://agarwal-labs.com/

## Local development

```sh
npm install
npm run dev
```

Passing pull-request tests publish a `portfolio-browser-check` build artifact for local UI review. This does not deploy the site.

## Portfolio views and Lab OS

The site defaults to Lab OS. Use `?view=os`, `?view=search`, `?view=journal`, `?view=forward`, `?view=training`, or `?view=terminal` to select a view explicitly; an earlier selection is otherwise remembered. All views also work with the development server.

- Both modern and retro desktops use a bottom Windows-style taskbar, Start app search, network status, time/date, and a calendar. Start also offers restart, shutdown, full-page views, and icon arrangement reset.
- Desktop defaults are grouped into rows: Sid Search, Projects, Library, and GitHub; Forward pass and Other designs; then Games, Markets, Launches, and AI leaderboards. Resume.pdf and README.txt start at the bottom-left. Projects contains arXiv Search, NVDocs RAG, HireMe.AI, Financial models, and Reader; Other designs contains Training run, Terminal, and Journal; Games contains Snake, Mines, Blocks, Rank It, and Next Token. The Start menu and the phone home screen use the same folders (`menuSections` in `src/features/views/os/apps.ts`), so the phone home screen stays at 12 icons, and Start search still finds apps inside folders and names the folder each one is in. Sid Search opens beside the four-column default icon area when space permits.
- The **arXiv Search** app's Overview tab shows Source R@10, Source MRR@10, the corpus size, and nDCG@10 from tuned BM25 (0.5068) to the current reranker (0.8418), with a hill-climbing chart and table of ten milestones. The numbers come from arxiv-search's `docs/06-charts.md` at commit ffd60e2 and live in `src/content/arxivSearch.ts`; the last milestone is scored on 3,678 relevance judgments and the others on 3,579, which the app notes. Its Try it live tab frames https://arxiv.agarwal-labs.com, which allows framing by agarwal-labs.com and posts `{ type: "arxiv-search:ready" }` to the parent named by the frame's referrer. If that message doesn't arrive within 6 seconds (the site is down, or the page runs on another origin, such as a local build), the tab reports the failure and offers a new tab. NVDocs RAG, HireMe.AI, and Financial models open their repositories in the GitHub app, and Reader still opens directly from Microsoft links. In Sid Search, arXiv Search appears as a regular project in the Projects list and as a ranked result for matching searches; inside Lab OS, links to arxiv.agarwal-labs.com open the arXiv Search app, and elsewhere they go to the live site.
- Desktop icons snap to a grid and retain their positions in browser storage. Drag them, or focus an icon and use Shift + arrow keys. Dropping on another icon swaps their positions. The grouped layout uses `lab-os-icons-v2`, so it replaces old `v1` arrangements once; new custom positions survive reloads, and Arrange restores the grouped defaults.
- Drag window title bars to move them, any edge or corner to resize, and double-click the title bar to maximize. Show desktop temporarily minimizes open windows; its second click restores them. Phones use a home screen and full-screen apps instead.
- Portfolio apps have independent browser history. Markets, Launches, and AI leaderboards are full pages (see [Live pages](#live-pages)) that open as desktop apps; the taskbar widgets for NVDA, the next SpaceX launch, and the top Arena text model open them. Embedded apps do not repeat the ticker. A link from any app to one of these pages opens, or navigates, that page's own window. If the OS doesn't confirm that within half a second (a Lab OS tab left open across a deploy can run an OS that predates these apps), the page opens in the window that held the link instead.
- Games include Snake, Mines, Blocks (an original Tetris-style falling-block puzzle), Rank It, and Next Token. Snake and Blocks pause when inactive or the browser tab is hidden. Controls work with keyboards and on-screen buttons.
- Restart resets the open apps and boots directly into the actual desktop, rather than displaying a separate decorative desktop first.

Forward pass and Training run use a real miniature transformer language model trained in a Web Worker: one block with 16-dimensional learned word and position embeddings, 2-head causal self-attention with learned query, key, value, and output projections, a GELU feed-forward layer (16 → 64 → 16), RMSNorm, residual connections, and a next-word output layer. It has 10,553 parameters, hand-written backpropagation (checked against finite differences), and AdamW. Press Train to run 12 epochs at a time, capped at 24; pause and deterministic reset are available. The corpus is fixed public portfolio text plus a few ML and search explainer sentences, with every fifth document held out and the vocabulary built from training documents only. The graph shows measured cross-entropy: training loss falls steadily while held-out loss bottoms out after about four epochs and then drifts up, and the UI shows the best held-out epoch beside uniform and word-frequency baselines. Model weights stay in memory and each view owns an independent instance. No download, inference API, or visitor-data collection is involved.

Forward pass displays the mini model's actual learned attention, averaged or per head, and its next-word probabilities; words seen too rarely to enter the vocabulary appear as "rare word". Project matching, contact sampling, and notebook cell execution remain explicitly labeled illustrations, not outputs of this model. This is a learning demo, not a chatbot.

**Pretrained transformer.** The Forward pass view's "Pretrained weights" section also runs Andrej Karpathy's [stories260K](https://huggingface.co/karpathy/tinyllamas/tree/main/stories260K) (260,032 parameters, Llama 2 architecture with grouped-query attention, trained on TinyStories) entirely in the browser through a dependency-free TypeScript port of [llama2.c](https://github.com/karpathy/llama2.c)'s `run.c`, showing the real attention for every layer and head. The 1.06 MB model downloads only after the visitor presses Load. Tests check that greedy output matches llama2.c's documented `run.c` output token for token. Weights are MIT licensed; see `public/models/stories260K/README.md` for the source revision, SHA-256 hashes, and license.

**Rank It: Beat my search engine** (Lab OS → Games). Six real development queries from arXiv Search (commit ffd60e2), each with 5 papers graded 0–2 by AI judges. Reorder the papers, then compare your nDCG@5 with the saved rankings from the tuned BM25 baseline and the latest AI reranker on the same papers. Data is built by `scripts/build-rankit-data.mjs <arxiv-search clone>`, which checks the project's published nDCG@10 (0.5068 with 3,579 judgments; 0.8418 with 3,678) before writing anything. Scores use 5 papers per query, so they differ from the project's nDCG@10, and the grades are AI-made, not validated by people.

**Next Token** (Lab OS → Games) shows real next-token probabilities from [SmolLM2-135M](https://huggingface.co/HuggingFaceTB/SmolLM2-135M) (Hugging Face, Apache 2.0). **Guess the next token** is the no-download game with seven saved predictions. **Try your own prompt** runs the same small text-completion model locally, not a smarter model or a chatbot; it can be wrong or repetitive. Both modes use real model predictions.

`npm run data:next-token` (`scripts/precompute-next-token.mjs`) runs `onnx-community/SmolLM2-135M-ONNX` (q4f16, pinned revision) with transformers.js in Node, caching weights in `node_modules/.cache/huggingface`. For each prompt it stores the top 8 logits and the full-vocabulary log-sum-exp at temperatures 0.2–2.0, so every probability and the "all other tokens" bar is exact. The custom-prompt tab runs that model in a Web Worker (WebGPU or WebAssembly). The first download of about 120 MB from Hugging Face, plus ONNX Runtime from jsDelivr, requires pressing "Load model". Reopening checks the actual browser cache for every file of the pinned revision, including the external ONNX weights, rather than trusting a "downloaded" flag. When those files remain available, the app opens the live France prompt automatically while initializing the saved model; editing is available immediately and inference waits until it is ready. Closing still releases the worker and its memory. Missing, partial, older-revision, or cleared caches require download confirmation again, including if files disappear during restoration. Cache inspection failures are explained and manual loading remains available. The runtime may still need a network connection if its own cached files are unavailable. `vite.config.ts` sets the `onnxruntime-web-use-extern-wasm` condition so the build doesn't emit an unused 27 MB WebAssembly copy, and the deploy workflow skips `onnxruntime-node`'s CUDA download.

Run the focused checks with `npm run test:e2e -- views.spec.ts models-games.spec.ts pretrained-model.spec.ts rankit.spec.ts next-token.spec.ts next-token-inference.spec.ts`, or all browser regressions with `npm run test:e2e`. Both commands build first; the focused checks also verify genuine loss reduction, a finite-difference gradient check, causal attention, deterministic resets, the stories260K greedy match, Rank It and Next Token data integrity, inference validation, and the falling-block engine.

Before enabling live inference, the worker checks two saved prompts with different sequence lengths. It requires the expected input/vocabulary sizes, finite scores, the correct top token, and probabilities within five percentage points of the native CPU reference. A GPU that fails initialization or the calculation check is disposed and retried on WebAssembly using the same cached weights; the UI explains the fallback. If WebAssembly also fails, live inference remains unavailable rather than displaying unverified predictions. This retains the existing 120 MB download.

`npm run test:models` is a separate, real-inference check: it downloads the pinned Next Token model and compares native CPU predictions with the production browser worker on WebAssembly for all seven prompts. It requires identical input token IDs and top choices, normalized probabilities, and at most five percentage points difference for the browser's top 32 probabilities at temperature 1. This is deliberately not bitwise parity: the model's `MatMulNBits` nodes use `accuracy_level=4`, and [ONNX Runtime's native CPU implementation](https://github.com/microsoft/onnxruntime/blob/v1.30.0/onnxruntime/contrib_ops/cpu/quantization/matmul_nbits.cc) permits int8 activation quantization when supported. Initial measurements found up to 3.5 percentage points of native CPU/browser drift despite matching top choices. The original one-percentage-point diagnostic exposed that assumption; the five-point bound is tested explicitly, alongside exact top-choice agreement. Reports retain the measured error rather than hiding it.

Set `NEXT_TOKEN_DEVICE=webgpu` to test an actual available GPU, or `NEXT_TOKEN_DTYPE=q4` to compare float32 computation with `q4f16`. A requested GPU must actually run; falling back does not count as passing a GPU check. The model-parity workflow runs these network-dependent checks separately from the mocked UI suite. On the tested Qualcomm Adreno 7xx GPU, the old `q4f16` path disagreed with the CPU top choice on six of seven prompts; WebAssembly matched all seven. `q4` also restored those rankings on that GPU but increases the download from about 120 MB to 184 MB, so it is a diagnostic alternative, not a silent default-model replacement.

### Larger-model investigation

On 2026-11-10, the actual browser worker was used to probe these configurations on a Qualcomm Adreno 7xx. Each measured pass used the seven saved prompts, top 8 results, and the same temperature grid. These are observed single-step times after startup, including probability calculation and any first-shape shader compilation, not a standardized throughput benchmark. Probabilities below are at T = 1; different tokenizers also make these unsuitable as a cross-model accuracy score.

| Model / backend | Model files | Step time | First token after "The capital of France is" | First token after the Eiffel Tower prompt |
|---|---:|---:|---|---|
| Current SmolLM2-135M q4f16 / verified WASM | 120 MB | 328-383 ms | ` the` (39.9%) | ` Paris` (27.2%) |
| [SmolLM2-360M q4](https://huggingface.co/onnx-community/SmolLM2-360M-ONNX/tree/539c1088be2dcd673c39059d25a6bc4aec625504) / WebGPU | 390 MB | 138-564 ms | ` the` (20.1%) | ` Paris` (81.4%) |
| [Qwen2.5-0.5B q4](https://huggingface.co/onnx-community/Qwen2.5-0.5B/tree/bae5ceaee026f0d0592858b2bd27645a06f19c42) / WebGPU | 793 MB | 303-578 ms | ` Paris` (34.2%) | ` Paris` (46.7%) |

Cold download/startup took about 151 seconds for 360M and 311 seconds for Qwen on that connection. Both larger, single-file ONNX weight files failed Cache Storage writes in this browser: their tokenizer/configuration files were cached, but the weights were absent. Neither larger model has yet passed the native CPU/browser parity and cached-reopening acceptance checks.

Ten-token greedy continuations also exposed limits that the first-token table hides:

- The current 135M model continued the France prompt with "the capital of the United States." Correct inference does not make this small model factually reliable.
- 360M repeated "the capital of France, which is the capital of" for France, although it produced Tokyo for Japan and Au for gold.
- Qwen started with Paris for France, then repeated itself. For Japan and gold, it continued in multiple-choice-question format rather than giving direct answers within the ten-token limit.

The default therefore remains 120 MB; there is no silent model upgrade or extra download. A larger optional model needs reliable caching, its own matching reference predictions, explicit download consent, and broader completion evaluation first. These limited probes are not evidence of chatbot-level quality.

## Market ticker

In full-page portfolio views, stock quotes and custom metrics move together on one native scrolling track with matching typography. Lab OS uses compact taskbar widgets instead. The ticker never loads TradingView; charts load only on `/markets`. An imminent SpaceX launch pins its countdown and watch action to the left of the full-page ticker while the remaining items continue scrolling to its right. Hovering or focusing the watch action does not pause the track. Hovering the scrolling area pauses it; keyboard focus within it and reduced-motion preferences make it a static, horizontally scrollable row. The full-page ticker has no on/off control, and any previously saved off preference is ignored.

`useStockQuotes` uses the existing `VITE_FINNHUB_KEY` configuration and refreshes the seven symbols once per minute while the page is visible. The existing GitHub Actions deployment already reads this value from its repository secret; local development reads Vite's environment files. Quote timestamps, source, delay information, and cached status are available in each stock's hover text, not as a separate scrolling item. Failed requests retain real cached quotes or show "Unavailable" if there is no quote. Prices are never simulated.

Vite variables prefixed with `VITE_` are public in the client bundle. This follows the original site's quote configuration; a credential that must remain private needs a server-side proxy instead. Never put unrelated private credentials in these variables.

The same track includes:

- **SpaceX:** the next SpaceX launch from [The Space Devs' Launch Library 2](https://thespacedevs.com/llapi), using the detailed response for official webcast links. The countdown advances once per minute; schedules refresh after two hours, or 15 minutes inside the four-hour launch window. Failed requests retain the last successful schedule and retry after 15 minutes. Stale data shows "Schedule cached"; missing data links to "Check schedule". A confirmed, fresh launch less than four hours away is highlighted in a fixed left-side slot, ahead of the scrolling items, instead of appearing in the scrolling loop. The action uses an HTTPS official webcast on an allowed host, or says "Launch details" when no verified stream is available. "Stream live" requires an explicit feed signal. Tentative and stale schedules never trigger the highlight. Passing the scheduled time shows "Awaiting update", not a claim that the launch happened.
- **Mars gravity:** a fixed reference value of 3.71 m/s squared.
- **Highest ELO LLM:** the model name, score, and date from [Arena's overall text leaderboard](https://arena.ai/leaderboard/text), ranked by point-estimate score. This is a manually verified, visibly dated snapshot, not a live feed. Update `arenaLeader` in `src/content/journalContent.ts` after checking the leaderboard; preserve its update date and score uncertainty. The September 2, 2026 snapshot, checked September 5, has claude-fable-5 at 1507 (+/-5). Overlapping ranking intervals do not establish a definitive best model.

The old combined stock/launch/simulated-telemetry hook is not imported. The native quote hook and existing launch hook each run once, not once per visual copy of the scrolling loop.

With the Vite dev server running, open `/?launch-preview=soon` for a labeled mock countdown starting at T-2h 14m. The mock uses an official O3b mPower webcast link verified September 10, 2026, but its countdown is simulated. It does not fetch or overwrite cached launch data and is disabled in production builds. Reloading restarts the preview.

The launch schedule and recent launches show loading messages while requests are pending, including when rechecking an expired empty cache or retrying a failed request. Previously loaded launch details stay visible during refreshes. The **Test portfolio** GitHub Actions workflow builds and runs the full Playwright suite in Chromium on pull requests to `main` and on manual dispatch. Failed runs upload Playwright's screenshots, traces, and videos for seven days. This check does not deploy the site.

## GitHub app data

The Lab OS GitHub app reads normalized `GitHubInsights` (`src/features/views/os/github/contract.ts`) through `src/features/views/os/github/client.ts`:

- **Own profile (sidagarwal-labs):** the build-time snapshot `src/content/generated/github-insights.json`, written by `npm run data:github` (`scripts/fetch-github-insights.mjs`) from GitHub's GraphQL API: the full-year contribution calendar, totals, and up to 30 public repositories with per-day commit activity. Repositories with commits in that year also get `allTimeCommits`, the user's commits on the default branch since the repository began, from a second query (`history(author:)`); if only that query fails, the snapshot is still written without it. The Top repositories list labels both: commit contributions in the last 12 months (default branch, a squash-merged pull request counting once) and the all-time count. It needs `GITHUB_TOKEN` or `GH_TOKEN` (PowerShell: `$env:GITHUB_TOKEN = (gh auth token); npm run data:github`). The deploy workflow refreshes it before every build, on each push to `main` and in the daily run (09:17 UTC), using the workflow's own token. Without a token, or if the fetch or validation fails, the committed snapshot is kept and the script exits 0; it exits 1 only when no usable snapshot exists. `GITHUB_INSIGHTS_LOGIN` overrides the login.
- **Other users:** when the build sets `VITE_GITHUB_PROXY_URL`, the app calls `GET <proxy>/github/v1/users/:login` on the Cloudflare Worker in `workers/github-proxy`. It runs the same GraphQL queries and normalizer (`workers/github-proxy/src/insights.mjs`) with a server-side token, caches responses at the edge for 6 hours (unknown users for 1 hour), allows 30 requests per minute per IP in each Cloudflare location, and only sends CORS headers to agarwal-labs.com, www.agarwal-labs.com, and `http://localhost`/`http://127.0.0.1` on any port. If the proxy is unset, unreachable, or failing, the app falls back to GitHub's unauthenticated REST API: the last 90 days of public events, counting pushes rather than commits and without all-time counts, within GitHub's 60 requests per hour per IP.
- **Privacy:** private repositories are never named. Private work appears only as anonymous calendar counts and the `restricted` total, and the snapshot script rejects output containing any repository GitHub reports as private.

`npm run test:worker` runs the normalizer and Worker tests with Node's test runner and mocked GitHub responses. `tests/e2e/github-client.spec.ts` covers the client, the REST fallback, and the committed snapshot.

### One-time proxy setup

The site works without these steps; other users then get the 90-day public-events view.

1. **Cloudflare API token.** A Worker custom domain needs an active Cloudflare zone, and agarwal-labs.com already uses Cloudflare DNS. In the Cloudflare dashboard, create an API token from the **Edit Cloudflare Workers** template ([Cloudflare's GitHub Actions guide](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/)), restricted to this account and the agarwal-labs.com zone. The essential permissions are Account › Workers Scripts › Edit (creating the Worker on the first deploy needs product-level Workers Admin in Cloudflare's newer role model) and Zone › Workers Routes › Edit for agarwal-labs.com, which adding a Custom Domain requires ([Workers roles and permissions](https://developers.cloudflare.com/workers/authorization/workers/)). Keep Workers Routes on the token: with `workers_dev = false`, later deploys also read the zone's routes ([workers-sdk#15863](https://github.com/cloudflare/workers-sdk/issues/15863)).
2. **Cloudflare account ID:** shown on the dashboard's Workers & Pages overview ([Find account and zone IDs](https://developers.cloudflare.com/fundamentals/account/find-account-and-zone-ids/)).
3. **GitHub token for the proxy:** a fine-grained personal access token with Repository access set to **Public repositories (read-only)** and no other permissions. Set an expiry and renew it before it lapses.
4. Under Settings › Secrets and variables › Actions, add the repository secrets `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, and `GH_PROXY_TOKEN`.
5. Run the **GitHub proxy** workflow from the Actions tab. It runs the tests, deploys `agarwal-labs-github-proxy` to `api.agarwal-labs.com`, stores `GH_PROXY_TOKEN` as the Worker secret `GITHUB_TOKEN`, and checks `/health`. Without the three secrets, the deploy is skipped and the run still passes. Later pushes to `main` that change `workers/github-proxy/` redeploy it.
6. Add the repository **variable** `GH_PROXY_URL` = `https://api.agarwal-labs.com` (GitHub rejects variable names starting with `GITHUB_`), then rerun **Deploy Portfolio** so the build includes it.

**Current deployment:** the Worker is live at `https://api.agarwal-labs.com` (first deployed November 10, 2026). `GH_PROXY_TOKEN` is a 30-day fine-grained token that expires around **December 10, 2026**. Before then, create a new token with the same settings, run `gh secret set GH_PROXY_TOKEN --repo sidagarwal-labs/portfolio`, rerun the **GitHub proxy** workflow, and update this date. An expired token makes lookups of other users fall back to the 90-day public-events view.

For local Worker development, put `GITHUB_TOKEN=...` in `workers/github-proxy/.dev.vars` (git-ignored) and run `npx wrangler@4 dev` in that folder; set `VITE_GITHUB_PROXY_URL=http://localhost:8787` in `.env.local` to use it from the dev site.

## Verification

```sh
npm run build
npm run test:e2e
```

The test command builds in Vite's `test` mode with a non-secret fixture quote key, then starts a temporary preview on port 4175 with the real root `/` base path used by the custom domain. To use another port, for example to run several suites at once from separate worktrees, set `PLAYWRIGHT_PORT` (`PLAYWRIGHT_PORT=4181 npm run test:e2e`, or `$env:PLAYWRIGHT_PORT=4181; npm run test:e2e` in PowerShell). Tests cover desktop and mobile layouts, keyboard access, removed-note recovery, legacy links, GitHub Pages redirects, commit dates and caching, book thumbnails, launch scheduling, shared ticker motion, quote loading, failure, cleanup, and reduced-motion behavior, and the live pages' live, fallback, and failure states, plus the in-browser models (finite-difference gradient check, llama2.c greedy match) and the Rank It and Next Token data. Provider responses are mocked for repeatability, and the Next Token live model's Hugging Face and jsDelivr downloads are blocked. A normal `npm run build` uses the real configured key; the deploy command always performs that normal build first.

The production TypeScript project checks `src/main.tsx` and its transitive imports. Previous 3D pages, styles, and supporting dependencies remain in the repository but are not part of the deployed app. This also leaves unrelated work-in-progress pages untouched.

## Publish to GitHub Pages

Commit the website changes and push `main`:

```sh
git push origin main
```

The existing `.github/workflows/deploy.yml` workflow builds the app using the repository's `VITE_FINNHUB_KEY` secret and deploys the `dist` artifact to GitHub Pages. The Pages source should be set to GitHub Actions. The workflow also supports manual dispatch from the Actions tab.

Verify the completed deployment at https://agarwal-labs.com/. The custom domain is configured in the repository's Pages settings, and the old `sidagarwal-labs.github.io/portfolio/` URL redirects to it. The app is built for the domain root, so do not restore a `/portfolio/` base path. `public/404.html` preserves direct article links on GitHub Pages.

`npm run deploy` is the older branch-based publishing command. Use it only when Pages is explicitly configured to serve the `gh-pages` branch instead of the Actions workflow.
